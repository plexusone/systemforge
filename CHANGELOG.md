## [Unreleased]

### Highlights

- Access tokens are bound to the application they were issued for: relying parties, the session JWT service, and multi-app routing each refuse tokens minted for another application that shares the signing key
- SCIM credentials are bound to one organization: a customer's identity provider provisions only its own members and cannot change the identity of users who also belong elsewhere

### Breaking

- session/jwt: `Config.Audience` is required; `NewService` returns `ErrMissingAudience` without it. Client-kind audiences (`bff`, `api`, custom) are added in front of the application audience instead of replacing it, and `ValidateAccessTokenWithAudience` with an empty audience checks `Config.Audience` instead of skipping the check
- relyingparty: `VerifyAccessToken` accepts only tokens issued to `Config.ClientID` unless `AcceptedClientIDs` or `AccessTokenAudience` is set; client-credentials tokens from other clients must be listed
- multiapp: without `AppAudiences`, tokens on app routes must carry the app's `AppID` as an audience
- authz: `RequireResourceAction` no longer sets a resource's organization from the caller's token; extractor errors answer 400 for a missing or malformed ID, 403 for `ErrResourceNotFound`, and 500 otherwise
- scim/store: the Ent store refuses requests without a provisioning scope. For a tenant, `active` is the membership's state, creating a user who exists elsewhere links them as a member, deleting a shared user removes only the membership, and groups cannot be created, renamed or deleted

### Upgrade Guide

- session/jwt: set `Config.Audience` to a value naming the application. Access tokens issued before the upgrade are refused and clients refresh; refresh tokens issued without the audience require signing in again
- relyingparty: list in `AcceptedClientIDs` every client, including the application's own `ClientID`, whose tokens the API must accept, such as service clients using client credentials; or set `AccessTokenAudience` for an API that many clients call with an audience
- multiapp: mint tokens with `jwt.TokenOptions{Audience: []string{appID}}`, or set `AppAudiences` to the audiences your tokens already carry
- authzguardsql: handle `ErrNoAuthorizedEntities` from `PolicyBuilder.Build` by refusing the query (for example with 403)
- authz: replace `WithResourceID` with `WithResourceLookup` on routes whose access depends on the organization role, passing a lookup that returns the resource's owning organization
- scim: authenticate with `CredentialMiddleware` and bind each SCIM credential to its organization (`Scope{OrganizationID: ...}`); give `Scope{Platform: true}` only to platform operator credentials

### Security

- Relying-party bearer authentication accepted a SystemAuth access token issued to any other OAuth client, and an ID token, as an access token for the application, taking the organization memberships in its claims; `VerifyAccessToken` now requires a `client_id` claim from an accepted client and refuses typed non-access JWTs
- The session JWT service's default validation (`ValidateAccessToken`, `HTTPAuth`, `HTTPAuthOptional`) accepted tokens for any audience, so applications sharing a signing key accepted each other's access and refresh tokens; tokens must now carry the service's `Config.Audience`
- multiapp `AuthMiddleware` accepted a token minted for one app on every other app unless `AppAudiences` was set; a token on an app route must now be addressed to that app's ID by default
- authzguardsql `PolicyBuilder.Build` turned a principal authorized for no entity into a GuardSQL policy with empty allowlists, which GuardSQL reads as unrestricted, so the least-privileged principals could query every entity and field; it now returns `ErrNoAuthorizedEntities`
- authz `RequireResourceAction` checked a resource named in the request against the caller's role in the organization from their token, so a member of one organization passed resource checks for another organization's resources; the resource's organization now comes only from the extractor
- The SCIM store had no tenant scoping, so any SCIM credential could read, change, delete and regroup every user and organization on the platform; each request is now bound to the credential's organization, and requests without a scope are refused
- SCIM could rewrite the login email of a user who also belonged to other organizations, enabling account takeover; a tenant now changes email, name and photo only for users it provisioned that belong to no other organization, and manages only the membership of others
- Deactivating an organization membership left the member's organization role, application roles and resource grants in the SpiceDB graph, so under the ReBAC authorizer a deactivated admin kept every permission; deactivation now removes them from the graph and reactivation writes them back

### Added

- relyingparty: `Config.AcceptedClientIDs` lists the OAuth clients whose access tokens an application accepts
- systemauth: JWT access tokens carry the JOSE `typ` header `at+jwt` (RFC 9068)
- multiapp: `MiddlewareConfig.AllowCrossAppTokens` accepts tokens for every app when that is intended
- session/jwt: `Claims.HasAnyAudience` and `ErrMissingAudience`
- authzguardsql: `ErrNoAuthorizedEntities`
- authz: `WithResourceLookup` and `ResourceOrgLookup` load a resource's owning organization for `RequireResourceAction`, and `ErrResourceNotFound`
- scim: `Scope`, `WithScope`, `WithTenant`, `WithPlatformScope`, `ScopeFromContext`, and `API.CredentialMiddleware` with `Credential` to bind SCIM requests to an organization or the platform

### Deprecated

- scim: `API.Middleware`, which binds no provisioning scope; use `CredentialMiddleware`

- SCIM provisioning guide

## [v0.14.0] - 2026-10-11

### Highlights

- Managed principals: humans without an email, such as young learners, created and controlled by guardian and educator managers, who sign them in with QR-friendly login tokens; opt-in per deployment and per client (ADR-005)
- Principal is the sole identity root: the legacy User model and its dependent tables are removed, so password login, social login, federation sync, and SCIM all resolve a person to the same principal (ADR-004)
- Resource servers can authenticate AI agents with AAuth through a protocol-neutral request principal and authenticator chain shared with bearer, API-key, and BFF-session credentials
- Fixed a panic on every ascending SCIM list sort, including the default order
- Security: the marketplace, organization, and invite APIs act for the authenticated caller and check organization permissions, instead of trusting IDs in the request; invite tokens are stored hashed
- The simple and SpiceDB authorization providers grant the same organization and manager permissions, held to the base schema by a parity test and a shared conformance suite
- Organizations without a plan: a first social login creates the person's personal organization, slugs are reserved, renamed with a cooling-off period and aliases, a personal organization converts to a team, and what an organization may use comes from its marketplace subscriptions and licenses (ADR-006)
- Application roles per member, entitled through the marketplace, carried in the `orgs` claim and on invites, with relying parties reading memberships from claims by default (ADR-007)
- Real-time invalidation of access: access tokens default to 10 minutes and are capped at 15, every access-reducing change is recorded, and relying parties refuse tokens issued before it, with polling, replay and back-channel delivery (ADR-010)
- Resource-scoped collaborators: the `collaborator` organization role, resource grants with a standard viewer, contributor and maintainer ladder in both authorization modes, and invites that target one resource (ADR-008)
- The authorization mode is configuration: the `authz` key selects `rbac` or `rebac`, and `authz/mode.New` builds the provider, syncer and grant store (ADR-008)
- Management is derived from manager relationships; a manager can release a principal, a self-managed human can be invited to be managed or decline, and managing operations are authorized and served over HTTP (ADR-009)
- Editor and viewer are no longer organization roles, and the organization `plan` column is removed; run migrations 0004 to 0009 on existing PostgreSQL databases

### Upgrade Guide

- Run the migrations against an existing PostgreSQL database, in order: 0004_drop_organization_plan, 0005_subscriptions_per_listing, 0006_invite_app_roles, 0007_oauth_app_backchannel_logout_uri, 0008_drop_editor_viewer_roles and 0009_invite_resource_target. Each is idempotent. Fresh databases need none of them. Then run `systemauth migrate` for the new tables sf_app_roles, sf_slug_reservations, sf_access_changes, sf_resource_grants and sf_manager_invites
- Replace uses of the organization plan with entitlements: remove `Plan` from organization inputs and filters, and read `entitlements` from organization responses. Supply APIConfig.Entitlements with marketplace.EntitlementSource; carry a paid tier over as a subscription or license
- Replace `editor` and `viewer` in your own role tables, vocabularies and invites with `member` and `collaborator` (or resource roles); stored memberships are mapped by migration 0008, which records an access change for each active membership it changes
- Configure entitlements for application roles: build the approle service with marketplace.ApproleOptions(marketplace.EntitlementSource(...)), and declare applications free to everyone with marketplace.WithDefaultEntitlements. Without them no organization is entitled to anything, and marketplace.WarnIfNoEntitlements logs a startup warning
- Relying parties that depended on LocalMemberships must pass it explicitly. The default reads the `orgs` claim; use ClaimsOrRemoteMemberships to fall back to /oauth/userinfo/memberships when the claim is truncated or absent
- Pass a revocation cache to BearerMiddleware and NewBFF to refuse tokens issued before an access change; feed it with accesschange.ToSink in one process, the poller across replicas, or back-channel delivery across deployments. Review any configured access_token_lifetime against the 15 minute cap
- Build the authorization provider from configuration with `authz/mode.New(ctx, cfg.Authz, mode.Deps{...})` and pass its Syncer to the identity services. The `authz` key defaults to `rbac`. The `authz/simple` and `authz/spicedb` forwarding packages remain deprecated and will be removed in the next major release; import `authz/rbac` and `authz/rebac/spicedb`
- When switching to `rebac`, write existing memberships, application roles and resource grants into the graph through the syncer before serving requests, and write the composed schema (embedded instances always receive it; remote ones only with `write_schema`)
