# v0.39.0

**Release Date:** 2026-11-26

Work that every application repeated moves into SystemForge. A service whose
database schema is behind now refuses to start, instead of failing on the first
request that needs the missing column. An application builds its sign-in
buttons from the deployment, so a method turned on in SystemAuth's
configuration appears without a change to the application. And one package
decides what to show when a person has no name, so an email address is not
shown as one.

## A schema that is behind stops the service

- **Refuses to start.** When `systemauthsvc.New` is not asked to migrate
  (`--migrate=false`, or `Options.Migrate` off), it compares the database's
  tables and columns with the identity schema, on PostgreSQL and SQLite, and
  returns `ErrSchemaBehind` naming what is missing and how to fix it.
- **Check before a deploy.** `systemauth migrate --check` verifies the schema
  without changing it and exits non-zero if anything is missing. From Go, use
  `systemauthsvc.CheckMigrations` or `CheckSchema`.
- **Limits.** The check compares names only, not types, indexes or the
  PostgreSQL objects Ent cannot express. Passing does not prove the migration
  ran; failing proves it is needed. `Options.SkipSchemaCheck` opts out for a
  host that manages its schema by other means.

See [the schema must match the version](../systemauth/deployment.md#the-schema-must-match-the-version).

## Sign-in buttons from the deployment

- **Discovery.** SystemAuth publishes the methods its sign-in page offers as
  `sf_sign_in_methods_supported`, a SystemForge extension of the discovery
  document. `relyingparty.Client.SignInMethods` returns them.
- **BFF.** `GET /bff/auth/methods` answers
  `{"methods":[{"id","name","path"}]}`, in SystemAuth's order and limited to
  what the BFF can start (`github`, `google`, `email`).
  `BFFConfig.SignInMethods` overrides discovery, for a host that serves
  SystemAuth in the same process.
- **When it is read.** The relying party reads discovery when its client is
  built, so a method turned on later appears after the application restarts. A
  client built with `NewClientWithMetadata` makes no discovery request: set
  `BFFConfig.SignInMethods`.
- **Web.** The components that read the endpoint ship in the matching
  `systemforge-web` release.

See [relying parties](../systemauth/relying-party.md).

## One safe display name

The new package [`identity/displayname`](../design/adrs/ADR-024-names-are-supplied-not-derived.md)
turns a name, or nothing, into something safe to show: `Safe` returns the
trimmed name or `""`, `Or` takes a fallback, and `Show` falls back to
"Member". A value containing `@` is treated as no name.

The relying-party stores, `oauthclient`, the SCIM store and SystemAuth's
directories use it. This replaces the email fallbacks that remained in
consumers after v0.38.0.

## Changes to be aware of

- **Startup can now fail.** A deployment that starts without migrations and has
  not run one is refused. Run the migration, or `systemauth migrate --check`,
  before starting the new version.
- **The `name` claim can be absent.** SystemAuth leaves it out when the stored
  name is an address, as an account from before v0.38.0 may have. The address
  is still the `email` claim. A relying party must accept a missing `name`.
- **A name that is an address is no name.** A new account whose provider puts
  the address in the name field is asked for a name.
- **"Member" where the address was.** A relying-party store, SCIM or a
  federation sync that creates a principal with no usable name calls it
  "Member"; `oauthclient` uses the handle, else "Member".
- **Later writes keep the stored name.** A sign-in, a SCIM update or a
  federation update that carries no name, or an address, leaves the name as it
  is.
- **Stored names are not rewritten.** A name that is already an address stays
  in the database. Show it through `displayname.Show`.

The release adds no breaking change to the API.

## Upgrading

There is no new migration since v0.38.0. From an earlier version, run the
schema migration first: `systemauth migrate`, start with `--migrate`, or call
`systemauthsvc.Migrate`.

Upgrade SystemAuth first, then the applications: each application's BFF serves
`/bff/auth/methods` from what SystemAuth publishes, and against an older
SystemAuth the list is empty.

An application can then remove its hand-written provider list and its own
guard against showing an address, and use the endpoint and
`identity/displayname` instead.
