# v0.38.0

**Release Date:** 2026-11-25

A person's name is no longer made from their email address. An email sign-in
gave SystemAuth an address and nothing else, and SystemAuth filled the gaps
from it: the display name became the address itself, and the personal
organization was named and slugged from the part before the `@`. The display
name reaches every application in the `name` claim, and applications show it on
public profiles, in member lists and on printed certificates, so an address was
being published. SystemAuth now asks the person for their name instead.

## Names are asked, not derived

- **A new account is asked for its name.** When an account is about to be
  created for a login that gave no name, which is every email sign-in and any
  social login whose provider returns neither a name nor a handle, SystemAuth
  shows `/signup/name` before it creates anything. It asks for the person's name
  and, optionally, a name for their personal workspace. Every application that
  federates to SystemAuth then receives a real `name` claim, and none needs a
  name prompt of its own for new accounts.
- **What is accepted.** A name is up to 100 characters, printable, with runs of
  spaces made one, and not an email address (no `@`); a workspace name is up to 80. A refused answer keeps what was typed and leaves the sign-up waiting.
- **The sign-up waits, proven and bound to the browser.** The proven login is
  parked for 15 minutes under a cookie (`__Host-sf_signup_name`), and the form
  carries an origin check and a form token derived from that cookie. Answering
  uses the parked sign-up once, so two answers cannot create two accounts.
  Nothing is created until the form is answered.
- **Order.** The invite gate, then the age question, then the name: a person who
  will be refused is not asked for a name. An existing account is never asked.
- **No mail section needed.** A deployment with GitHub or Google and no `mail`
  section builds the token store that parks sign-ups too.

Nothing is made from the address any more: the display name is the name the
person gave, or the provider's handle (a GitHub login); the personal
organization takes the workspace name they gave, else their name, else their
handle; and its slug is the handle or a generated one. The only fallback left,
for a directory used without the name step, is the neutral name "Member".

See [ADR-024](../design/adrs/ADR-024-names-are-supplied-not-derived.md),
[Sign In with an Email Code](../systemauth/email-sign-in.md#names) and
[Launching with Email Sign-In](../guides/email-sign-in.md).

## Sign-in methods from the deployment

`SocialLoginConfig.SignInMethods` and `Server.SignInMethods` list the methods a
deployment offers, in the order its sign-in page lists them (`github`, `google`,
`email`). A host builds its sign-in buttons from it, so a method turned on in
configuration shows up without a change to the host. The server's list includes
connectors passed in code.

## Fixed

- **Linked providers on the sign-in methods page.** The wrappers around account
  creation hid the directory's optional interfaces, so a deployment with an
  invite gate or an age check lost the page's list of linked providers and
  offered every provider again. They are read from the directory itself.

## Changes to be aware of

- **One more step for logins with no name.** Email sign-ins are always asked.
  GitHub gives its handle when a profile has no display name, so only a login
  with neither is asked; a Google account that returns no name is asked.
- **Slugs for Google accounts.** A new Google account's personal organization
  gets a generated slug, not its address's local part.
- **Existing accounts keep the names they have.** An account created by email
  before this release may still have its address as its name; changing a name
  is not offered yet. An application should not print a name that is an address.
- **Consumer-side fallbacks remain.** The relying-party stores and
  `oauthclient` still use the address when a host receives no name. SystemAuth
  now always sends one for a new account, so they apply only to older accounts
  and other identity providers.
- **`ExternalLogin.OrganizationName`** carries the workspace name given at
  sign-up. A host that calls `PrincipalDirectory.CreateFromExternal` directly,
  without the name step, gets the display name "Member" instead of the address.

The release adds no breaking change to the API.

## Upgrading

From v0.37.0 there is no migration: the new `sign_up_name` token purpose is a
plain value of an existing column. Set `social_login` as before; nothing needs
enabling.

From an earlier version, apply v0.37.0's migration first (`systemauth migrate`,
`systemauthsvc.Migrate` in a normal deploy, or
`migrations/0013_verification_token_attempts.sql`). v0.38.0 parks every sign-up
that needs a name in the verification token store, with or without a `mail`
section, so without the `attempts` column new sign-ups fail, not only email
sign-in.

A host that built its own name prompt for email accounts can drop it for new
accounts and keep a guard for old ones: never show or print a name that is an
email address. Build sign-in buttons from `SignInMethods()` instead of listing
providers by hand.
