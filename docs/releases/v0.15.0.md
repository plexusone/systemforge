# v0.15.0

**Release Date:** 2026-10-11

A breaking release that completes the organization model. **Organizations
without a plan**: a first social login creates a person's personal
organization, slugs are reserved and can be renamed with a cooling-off
period and aliases, a personal organization converts to a team, and what an
organization may use comes from its marketplace subscriptions and licenses
(ADR-006). **Application roles and claims**: each member holds a role per
entitled application, carried in an `orgs` claim and on invites, and relying
parties read memberships from claims (ADR-007). **Collaborators and
resource grants**: a `collaborator` organization role and resource grants in
both authorization modes (ADR-008). **Real-time invalidation**: tokens are
short-lived and relying parties refuse tokens issued before an access change
(ADR-010). Management is now derived from manager relationships (ADR-009).
Read the upgrade notes before deploying.

## Highlights

- **No organization plan** — `sf_organizations.plan` and `organization.Plan*` are gone; organization responses carry `entitlements` derived from the marketplace. See [Application roles and entitlements](../guides/application-roles.md).
- **Slugs** — reserved names, rename with a 7-day cooling-off period, aliases for old links, and personal-to-team conversion. See [Organization slugs](../guides/organization-slugs.md) and [Converting a personal organization to a team](../guides/personal-to-team.md).
- **Application roles** — assigned per principal, organization and application, limited to entitled applications and seat limits, and granted by invites. See [Invites](../guides/invites.md).
- **`orgs` claim and membership sources** — `ClaimsMemberships` is the default relying-party source; `RemoteMemberships` reads `GET /oauth/userinfo/memberships`.
- **Real-time invalidation** — access tokens default to 10 minutes (at most 15), every access-reducing change is recorded in `sf_access_changes`, and relying parties refuse earlier tokens; polling, replay and back-channel delivery cover replicas and separate deployments. See [Access-change invalidation](../guides/access-change-invalidation.md).
- **Collaborators and resource grants** — `viewer`, `contributor` and `maintainer` on one resource, in `rbac` and `rebac`, and invites that target a resource. See [Collaborators and resource grants](../guides/collaborators.md).
- **Authorization mode as configuration** — the `authz` key and `authz/mode.New`. See [Configuring the authorization mode](../guides/authorization-mode.md).
- **Management is a relationship** — release, manager invitations (accept or decline), authorized managing operations and deletion.

## Upgrade Notes

### 1. Database

Run these against an existing PostgreSQL database, in order; each is safe to
run more than once. A fresh database needs only `systemauth migrate`.

| Script | What |
|--------|------|
| `migrations/0004_drop_organization_plan.sql` | Drops `sf_organizations.plan` |
| `migrations/0005_subscriptions_per_listing.sql` | Adds `listing_id` to subscriptions and allows one subscription per listing beside the platform subscription |
| `migrations/0006_invite_app_roles.sql` | Adds `sf_invites.app_roles` |
| `migrations/0007_oauth_app_backchannel_logout_uri.sql` | Adds `sf_oauth_apps.backchannel_logout_uri` |
| `migrations/0008_drop_editor_viewer_roles.sql` | Maps `editor` to `member` and `viewer` to `collaborator` in memberships and pending invites, recording an access change for each active membership it changes |
| `migrations/0009_invite_resource_target.sql` | Adds the resource target columns to `sf_invites` |

Then run `systemauth migrate` (or `systemauthsvc.Service.Migrate`) for the
new tables `sf_app_roles`, `sf_slug_reservations`, `sf_access_changes`,
`sf_resource_grants` and `sf_manager_invites`.

### 2. Organization roles and the plan

- `editor` and `viewer` are no longer organization roles. The roles are `owner`, `admin`, `member` and `collaborator`; any other value is refused with `ErrInvalidRole`. Replace them in your own tables, vocabularies and invites; use resource roles for access to one resource.
- Remove `Plan` from organization inputs and filters, and from API requests. Supply `APIConfig.Entitlements` with `marketplace.EntitlementSource` to return `entitlements`.

### 3. Entitlements fail closed

An `approle.Service` with no entitlement source entitles no organization to
any application. Build it with `marketplace.ApproleOptions(src)`, and declare
applications free to everyone with `marketplace.WithDefaultEntitlements`.
`approle.EntitleAll` is for development and tests. `marketplace.WarnIfNoEntitlements`
logs a startup warning when nothing entitles anyone.

### 4. Relying parties read claims

The default membership source is `ClaimsMemberships`, which decodes the
`orgs` claim. `LocalMemberships` is no longer picked up implicitly; pass it
explicitly for development and tests. Use `ClaimsOrRemoteMemberships` when
the claim may be truncated or absent.

### 5. Token lifetime and revocation

The default access token lifetime is 10 minutes (it was 15), a configured
value above 15 minutes is refused at load, and per-client values are capped.
Pass a `relyingparty.RevocationCache` to `BearerMiddleware` and `NewBFF`, and
feed it as described in [Access-change invalidation](../guides/access-change-invalidation.md).

### 6. Authorization schema and packages

- The marketplace SpiceDB fragment attaches to the base organization through a `marketplace_org` facet and no longer redefines `principal` or `organization`. Compose schemas with `MergeSchema`, or let `authz/mode.New` compose and write them.
- Build the provider from configuration with `authz/mode.New`. The `authz/simple` and `authz/spicedb` forwarding packages (renamed in v0.14.0) remain deprecated and will be removed in the next major release; import `authz/rbac` and `authz/rebac/spicedb`.
- Switching to `rebac` starts with an empty graph; write existing memberships, application roles and grants through the syncer before serving requests.

## New Features

- Signup on first social login (`signup.SlugForLogin`, `CreatePersonalOrgInTx`, `EnsurePersonalOrgInTx`); reserved slugs (`organization.ReservedSlugs`, `WithReservedSlugs`); `Rename`, `ResolveSlug`, `WithSlugCoolingOff`; `ConvertToTeam`; personal organization rules (`ErrPersonalOrganization`).
- `identity/approle`: `Assign`, `Change`, `Remove`, `RemoveForMember`, `EffectiveRoles`, endpoints under `/organizations/{slug}/members/{principal_id}/app-roles`, and `authz.AppRoleSyncer`.
- `marketplace`: `EntitlementSource`, `ApproleOptions`, `WithDefaultEntitlements`, `WarnIfNoEntitlements`; listings may name an application and subscriptions may be per listing.
- `systemauth`: the `orgs` claim, `GET /oauth/userinfo/memberships`, `GET /access-changes`, `NewBackchannel`, and the `backchannel_logout_uri` client setting.
- `identity/accesschange`, `relyingparty.RevocationCache`, `NewAccessChangePoller`, `Replay`, `BackchannelHandler`; relying-party membership sources `ClaimsMemberships`, `RemoteMemberships`, `ClaimsOrRemoteMemberships`, `ProvisioningMemberships`.
- `identity/resourcegrant`, the resource-role ladder and `authz.ResourceGranter`; `rbac.WithResourceGrants`; resource-targeted invites.
- `authz.ModeConfig`, `authz/mode.New` and `systemauth.Config.Authz`.
- `identity/managedprincipal`: `Release`, manager invitations with accept and decline, `Delete`, and the managing operations over HTTP.

## Fixes

- Accepting an invite, and social login signup, register memberships, principals and organizations with the authorization graph.
- Signup creates the principal and personal organization in one transaction.
- The application-role seat limit cannot be exceeded by concurrent assignments, and assigning with no seat left answers `409`.
- Manager authority checks for `AddManager`, `RemoveManager` and `Release` run inside the row-locked transaction, a managed principal is never a valid manager, and access-change reasons are accurate.
